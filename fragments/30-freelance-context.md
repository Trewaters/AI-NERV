# Freelance / client-work context

Norms that apply when a repo is client work rather than a personal project.

## Time and scope

- Work is tracked in Clockify. When a task wraps up, a one-line summary of what was done (suitable for a time entry description) is useful — offer it, don't invent hours.
- Stay inside the agreed scope of the task. If you notice adjacent problems worth fixing, list them as recommendations instead of fixing them unbilled.

## Client boundaries

- Client code, data, and credentials never leave the client's repo/infrastructure. Don't copy client code into other projects, examples, or shared templates.
- Don't reference one client's project, name, or code in another client's repo.
- Deliverables should not depend on my personal accounts or infrastructure — use the client's services, keys, and CI.

## Communication artifacts

- PR descriptions and commit messages may be read by the client: keep them professional, concrete, and free of internal shorthand.
- When a change has user-visible impact, note it in plain language (for changelogs / status updates), separate from the technical description.
